# Самостійна робота №15 — варіант 4

**Дисципліна:** Комп'ютерні та мікропроцесорні системи, організація комп'ютерних мереж  
**Тема:** Хмарні та контейнерні мережі, моніторинг  
**Варіант:** 4 — файлове сховище; об'єктне сховище доступне лише від API

## 1. Мережева схема

```text
                         Публічний сегмент
Користувач ── HTTPS/443 ──> [Frontend]
                                  │ HTTPS/443
                                  ▼
                         Приватний сегмент
                             [API]
                               │ S3 API/9000
                               ▼
                 Ізольований приватний сегмент
                     [Object Storage]
```

Назовні відкритий лише HTTPS-вхід до Frontend. API доступний із фронтенду через HTTPS, а сховище об'єктів — лише від API через порт S3-сумісного інтерфейсу `9000`; прямого зовнішнього доступу до нього немає.

## 2. Режим контейнерної мережі та виявлення сервісів

Для одного вузла або невеликого розгортання обирається **bridge**: сервіси розміщуються в ізольованій контейнерній мережі, а назовні публікується лише порт `443` фронтенду. Контейнерний DNS дозволяє API звертатися до сховища за ім'ям сервісу, наприклад `object-storage:9000`, а фронтенду — до `api:443`. Режим `host` не обрано, бо він прибирає частину мережевої ізоляції контейнерів і не потрібен цьому застосунку. `Overlay` доцільний для кількох вузлів/кластерного розгортання, але для однієї машини додає непотрібну складність.

## 3. Правила груп безпеки

| Сервіс | Дозволений вхідний порт | Дозволене джерело |
| --- | --- | --- |
| Frontend | TCP `443` | Інтернет-клієнти до публічного балансувальника/входу |
| API | TCP `443` | Лише Frontend у приватній контейнерній мережі |
| Object Storage | TCP `9000` | Лише API у приватному сегменті; без публічного правила входу |

Усі інші вхідні з'єднання за замовчуванням заборонені. Сховище не публікує порт на хост і не має дозволу прямого доступу з Frontend чи Інтернету.

## 4. Метрики та порядок діагностики

**Метрики моніторингу:**

- затримка відповіді API (p50/p95);
- частка HTTP-помилок 4xx/5xx;
- стан healthcheck для Frontend, API і сховища;
- використання CPU та пам'яті кожним сервісом;
- частка помилок/затримка запитів API до object storage.

**Порядок діагностики недоступності:**

1. Перевірити healthcheck, DNS-ім'я сервісу та доступність потрібного порту з дозволеного сегмента.
2. Перевірити логи Frontend/API, коди HTTP і помилки з'єднання з object storage.
3. Перевірити політики мережі/групи безпеки, стан вузла й ресурси контейнерів; після виправлення повторити healthcheck і контрольний запит.

## Контрольні запитання

1. **Чому базі даних чи черзі повідомлень зазвичай не варто відкривати порт назовні?** Публічний порт збільшує поверхню атаки та ризик підбору облікових даних, експлуатації помилок або витоку даних. Такі сервіси мають приймати з'єднання лише від конкретних внутрішніх компонентів.
2. **Який режим мережі підходить сервісу без потреби в максимальній ізоляції, і чому його рідко виправдано обирати?** `Host` дає контейнеру мережевий простір хоста й може бути доречним для спеціалізованих високопродуктивних сценаріїв, але зменшує ізоляцію та підвищує ризик конфлікту портів. Тому зазвичай обирають bridge або overlay відповідно до масштабу.
3. **Яку перевірку варто виконати першою при повідомленні «сервіс недоступний»?** Почати з найшвидшої перевірки healthcheck і доступності DNS/порту з потрібного джерела; це відділяє відмову процесу від проблеми мережевого шляху.

## Висновок

У файловому сховищі назовні доступний лише HTTPS-фронтенд. API та object storage розміщені у приватних мережевих сегментах, а сховище приймає запити тільки від API. Bridge-підхід, явні правила доступу та контроль healthcheck, затримки, помилок і ресурсів дають змогу зберігати ізоляцію й системно діагностувати відмови.
